# 層の分け方

このエディタで扱うテキストは、1 次元の文字列に収まらない部分（分数・ルート・
行列・場合分けなど）を「島」として二次元のまま持つ。

そのため、**「意味」「書き方（保存形式）」「見せ方（表示）」の 3 つを混ぜない**
ことが設計上いちばん大事になる。混ざると、保存形式を直すと表示が崩れ、表示を
直すとファイルが変わる、という状態になり、どちらも直せなくなる。

```
        structure   （意味）
       ／        ＼
  format          view
（保存形式）      （表示）
       ＼        ／
         editor  （操作）
           │
          app    （画面の組み立て・ファイル入出力）
```

## structure — 意味

`src/structure/`

- `text`   … 文書そのもの。行 = アイテム列。島は 1 アイテム
- `ast`    … 島の中身（`Row` / `Node`）と、その中の位置（`Cursor`）
- `edit`   … 島の中の編集コマンド
- `vocabulary` … 構造・記号の語彙（名前・字の表と、`\name` が何になるか）
- `plain`  … 二次元の構造を一次元の普通のテキストに読み下す
  （分数なら `a/b`）。保存形式ではない：読み戻せないし、記法も出てこない

**format も view も知らない。** 記法も DOM もここには出てこない。

**書いた順に読めること。** `/` が上に持ち上げるのは直前のひとつながり
（`ab/` なら `ab`）だから、下の行が受け取るのも同じくひとつながりで、それが
書き終わると（`+` や空白のような、続きでない文字が来ると）カーソルは構造の
外に戻る。`a/b + 1` は打ったとおりに読め、長い分母は `a/(b + 1)` と括弧で
書く。ルートや上付き・下付きも同じ（`√2 + 1`、`x^2 + 1`）。カーソルを動かした
時点でこの「待ち」は終わる — そこからは書いているのではなく直しているから。

## format — 保存形式

`src/format/`

- `islands`  … 本文から `$( … )` を切り出す／書き戻す
- `notation` … 島の中身と構造の相互変換
- `document` … ファイル 1 つ分の読み書き（`read` / `write` のみ）

**structure だけに依存する。** 画面がなくても読み書きできること、が条件。
`web_sys` などを使ってはいけない。

**ファイル以外に使わない。** クリップボードはファイルではないので、コピー・
ペーストがここを通ってはいけない（通っていたために、分数をコピーすると
記法の文字列が貼られていた）。`document` の入口を `read` / `write` の 2 つに
限っているのはそのためで、`tests/layering.rs` が機械的に落とす。

## view — 表示

`src/view/`

- `row`      … 行をひとつ描く。**唯一の描画コンポーネント**
- `document` … 行を並べ、カーソル・選択を置く
- `measure`  … 描いたものを測る。行のどの位置が画面のどこか、点が何の上か

**行はどこにあっても行。** 本文の行も、島の中も、分数の分子も、すべて `row`
が描く。行は自分の「path」で自分がどこにいるかを知り、本文の行だけが path を
持たない（空）。最上位が特別なのは **タブによる列揃えだけ**で、これは複数行に
またがる話だから `document` にある。字体は本文と同じ — 構造の中でも斜体には
しない。二次元であることは形（分数の罫線、根号）が示すもので、字体で示す
ものではない。

カーソル・選択は本文でも構造の中でも同じ 1 つの仕組み — 描いたものを測って
オーバーレイに矩形を置く。**置くことと測ることは分けてある**（`document` と
`measure`）。比例フォントで browser が組んだ後でしか位置は分からないので両方向
必要で、混ざっているとカーソルがずれたとき「置き方が悪いのか測り方が悪いのか」が
切り分けられない。IME の未確定文字も同じで、`row` がカーソルのある行に
そのまま差し込む。

**structure だけに依存する。** 表示するものを記法から作らない
（記法文字列を parse して描く、をしない）。

## editor — 操作

`src/editor/` はキー入力・選択・Undo・検索など「操作」で、上のすべてを使う。
ファイルの読み書きは `format::document`、描画は `view` に任せる。

- `model`   … 文書を編集する `Editor`。`history`（Undo 履歴）と
  `island`（島への橋渡し）を中に持つ
- `session` … ペインごとの台帳。誰が画面にいて誰にフォーカスがあるかと、
  変更が画面とシェルに届く道
- `commands` … 入力・IME・クリップボード・パレット・検索置換が文書に
  何をするか
- `keys` / `mouse` … キーとマウスの表。文書の中でのキーはここ、アプリの
  キー（ファイル・タブ・検索バー）は `app` の表、の 2 か所だけ
- `clipboard` … コピーした一片を控え、外に出す文字列は `structure::plain`。
  外の世界へは普通のテキストだけが出て、同じアプリに貼り直したときだけ
  控えてある構造が戻る。

## app — 画面の組み立て

`src/app/` はシェルで、`shell`（ペイン・タブ・ファイルの状態と操作）、
`panes`（タブ帯とエディタの置き場）、`palette`、`find`（検索バー）、
`keys`（アプリのショートカット）、`menu`（メニューの項目が何をするか）に
分かれる。

メニューそのものは OS のもので、`src-tauri/src/menu.rs` が組み立てる。選ばれた
項目は名前だけが `menu` イベントとして届き、何をするかは `app::menu` の 1 つの
表にある（`app::keys` も同じ表を通るので、項目とショートカットが二重にならない）。

## この分離を壊さないための仕掛け

`tests/layering.rs` がソースを読んで、次を機械的に落とす。

- `structure` が `view` / `editor` / DOM に触れている
- `format` が `view` / `editor` / DOM に触れている
- `view` が `format` に触れている
- `structure` / `view` / `editor` の製品コードが `$( … )` を書いている
- `format::document` がファイル 1 つ分の読み書き以外を外に出している

例外は 1 つだけで、`structure` の**テストのフィクスチャ**は記法で書いてよい
（構造をベタ書きするより読みやすいため）。製品コードでは禁止。
