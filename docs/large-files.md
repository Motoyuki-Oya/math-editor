# 巨大ファイルを開けるようにする

数ギガのファイルを開くために、今の構造のどこを差し替えればよいかの整理。
「簡単に切り替えられるようになっているか」という問いへの答えから始める。

## 結論を先に

**層は分かれているが、切り替えるだけでは済まない。** 今の実装は 2 か所で
「文書は全部メモリにあり、全部が画面にある」ことを前提にしている。

1. 文書は行の配列。`Text { lines: Vec<Vec<Item>> }`（`src/structure/text.rs:79`）。
   1 文字が `Item::Char(char)` の 1 要素で、`Vec` の要素として 24 バイト前後を
   食う。1 GB のテキストは素の文字数で 10 億文字なので、この持ち方では数十 GB
   になる。行の挿入・削除も `Vec::insert` / `drain` で、先頭近くを編集すると
   後ろ全部が動く。
2. 描画は毎回全行。`View::draw()` が `self.lines.set_inner_html("")` してから
   `for line in 0..text.line_count()` で全行の DOM を作り直す
   （`src/view/document.rs:91`）。1 万行でも 1 万要素、100 万行なら描画が終わらない。

つまり必要なのは「読み込みを遅くする」ことではなく、**文書の持ち方**と
**画面に出す量**の 2 つを別々に有限にすること。層の境界（structure / format /
view / editor）はそのままで足りる。

## 段取り

### 第 1 段: 見えている行だけ描く（数十 MB 級がまともになる）— 実装済み

`view` だけの話で、意味の層は触らない。

- `View::draw()` が全行ではなく、`root` のスクロール位置から求めた行の範囲だけ
  DOM を作る。上下に画面 1 つ分の余白を持たせる。
- 見えていない行の高さは、上下に空の詰め物（`height` だけを持つ要素）で埋める。
  行の高さは行によって違う（分数や行列があると高い）ので、測った行の高さは
  行番号ごとに覆えておき、まだ測っていない行は 1 行分の高さで見積もる。
  スクロールバーの長さがずれるのはこの見積りのせいで、ずれは触った行から順に
  直っていく。
- `measure` は「今 DOM にある行」しか測れなくなる。今も測る前に必ず
  `line_row()` で行の要素を引いているので、`None` の扱い（画面外の行は測らない）
  を増やすだけで済む。
- 折り返し・行番号・列揃えはこの範囲の中で今と同じに動く。ただし列揃え
  （`align_columns`）は「連続する行のかたまり」を見るので、かたまりが画面外まで
  続くときは画面外の行も測る必要がある。かたまりの上端・下端までは描く、という
  例外を持たせる。

これは今のコードの形のままできる。差分は `view/document.rs` と `view/measure.rs`
に収まる。

### 第 2 段: 文書を行の索引にする（数百 MB 級）

`structure::text::Text` の中身を差し替える。外から見える形
（`line()`, `line_len()`, `insert()`, `remove()`, `slice()`, `math_at_mut()`）は
変えない。ここが「切り替えられる」境界になる。

- 中身を **piece table** にする。元のファイルは読み込んだ 1 枚のバッファ（後述の
  第 3 段では mmap）で、編集はすべて「追記バッファへの追加」と「断片の並びの
  差し替え」。文字を 1 つずつ `Vec` の要素にしないので、素のテキストの
  メモリはファイルとほぼ同じ。
- 行の頭の位置を別に索引として持つ（行番号 → 断片の中の位置）。`Pos { line, col }`
  はそのまま使え、`line()` は索引を引いてその行の断片を返す。
- 島（`Item::Math(Row)`）は素の文字と混ぜず、位置をキーにした表で持つ。島は
  文書全体の中では少数なので、これはメモリの問題にならない。**素の文字を軽く
  持ち、二次元のものだけを重く持つ** のがこの設計の要点。
- `format`（保存形式）は今のまま。読むときは行ごとに解析して索引を作り、書くとき
  は断片を順に出す。

### 第 3 段: 読み込まないで開く（数ギガ級）

- ファイルを全部読まない。native 側で mmap（または範囲読み）し、行の頭の位置だけ
  先に走査する。走査は数ギガでもディスクの読み出し速度で済み、文字の解析は
  必要な行に触ったときだけ行う。
- frontend（wasm）にファイル全体を渡さない。今の `read_document` は
  `String` を 1 つ返しているので、これを **範囲を要求する経路**に変える
  （行 N から M を返す、という形）。ここが唯一の新しい IPC の形。
- **行の索引は全行分を持てない。** 50 GB で 1 行 50 バイトなら 10 億行あり、
  行の頭を u64 で持つだけで 8 GB になる。一定間隔（たとえば 1 万行ごと）の目印
  だけを持ち、間の行は目印から数える。`Pos { line, col }` の形は変えない。
- 開く時点でやるのは改行の走査だけだが、それでもファイルを 1 回舐める
  （1 GB/s なら 50 GB で 50 秒前後）。進捗を出して中断できるようにし、
  走査の結果を控えて 2 回目以降を省く。
- 保存は「新しいファイルに書いて置き換える」。全文をメモリに持たないので、
  触っていない範囲は元のファイルから直接流す。
- 検索は行の走査をそのまま使う。`editor::search` は今も行を順に見ているので、
  行を要求する経路の上でそのまま動く。ただし「すべて置換」は全行を触るため、
  進捗を出して中断できるようにする必要がある。

## この順で出す理由

- 第 1 段だけで、実際に開けるファイルの大きさが 2 桁変わる（描画が今の上限）。
  しかも `view` の中で終わるので、意味の層のテストはそのまま通る。
- 第 2 段は `Text` の外向きの形を変えないので、第 1 段の上に独立して積める。
  ここで初めて `structure` のテストが「持ち方に依らない」ことの検査になる。
- 第 3 段は IPC とファイル入出力の形が変わる（唯一 UI に影響が出る段: 開いた
  瞬間に全文の文字数を数えられなくなるので、ステータスバーの「N 文字」は
  「読んだところまで」か「行数だけ」に変わる）。

## 変えないもの

- 保存形式。
- 層の境界（`structure` は `view` / `editor` / `format` を知らない、など）。
- 「普通のテキストとして読み書きする」書き味。折り返し・行番号・列揃え・島の
  編集はすべて今のまま。
