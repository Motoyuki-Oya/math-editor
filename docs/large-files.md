# 巨大ファイルを開けるようにする

数ギガのファイルを開くために、今の構造のどこを差し替えればよいかの整理。
「簡単に切り替えられるようになっているか」という問いへの答えから始める。

## 結論を先に

**層は分かれているが、切り替えるだけでは済まない。** 今の実装は 2 か所で
「文書は全部メモリにあり、全部が画面にある」ことを前提にしている。

1. 文書は行の配列。`Text { lines: Vec<Row> }`、`Row = Vec<Node>`。
   1 文字が `NodeKind::Char(char)` の 1 要素なので、1 GB のテキストは素の文字数で
   10 億文字となり、この持ち方では数十 GB
   になる。行の挿入・削除も `Vec::insert` / `drain` で、先頭近くを編集すると
   後ろ全部が動く。
2. 描画は毎回全行。`View::draw()` が `self.lines.set_inner_html("")` してから
   `for line in 0..text.line_count()` で全行の DOM を作り直す
   （`src/view/document.rs:91`）。1 万行でも 1 万要素、100 万行なら描画が終わらない。

つまり必要なのは「読み込みを遅くする」ことではなく、**文書の持ち方**と
**画面に出す量**の 2 つを別々に有限にすること。層の境界（structure / format /
view / editor）はそのままで足りる。

## 段取り

### 第 1 段: 見えている行だけ描く（数十 MB 級がまともになる）— 実装済み

`view` だけの話で、意味の層は触らない。

- `View::draw()` が全行ではなく、`root` のスクロール位置から求めた行の範囲だけ
  DOM を作る。上下に画面 1 つ分の余白を持たせる。
- 見えていない行の高さは、上下に空の詰め物（`height` だけを持つ要素）で埋める。
  行の高さは行によって違う（分数や行列があると高い）ので、測った行の高さは
  行番号ごとに覆えておき、まだ測っていない行は 1 行分の高さで見積もる。
  スクロールバーの長さがずれるのはこの見積りのせいで、ずれは触った行から順に
  直っていく。
- `measure` は「今 DOM にある行」しか測れなくなる。今も測る前に必ず
  `line_row()` で行の要素を引いているので、`None` の扱い（画面外の行は測らない）
  を増やすだけで済む。
- 折り返し・行番号・列揃えはこの範囲の中で今と同じに動く。ただし列揃え
  （`align_columns`）は「連続する行のかたまり」を見るので、かたまりが画面外まで
  続くときは画面外の行も測る必要がある。かたまりの上端・下端までは描く、という
  例外を持たせる。

これは今のコードの形のままできる。差分は `view/document.rs` と `view/measure.rs`
に収まる。

### 第 2 段: 文書の持ち方を軽くする（数百 MB 級）— 実装済み

`structure::text::Text` の中身を差し替えた。外から見える形
（`line()`, `line_len()`, `insert()`, `remove()`, `slice()`）は変えていない。

- 行を 2 つの持ち方にした。`$` を含まない素のテキストの行は**文字列のまま**
  持ち（`Line::Raw`）、`Row = Vec<Node>` への展開（1 文字 ≒ 100 バイト）は
  初めて `Row` として見られたときに行って共有する。構造や `$` を含む行だけを
  読み込み時に解析する。巨大なファイルの大部分は素の行なので、メモリは
  ファイルとほぼ同じで済む。
- 行は `Rc` で持ち、元に戻す履歴のスナップショット（`Text` の複製）は行を
  共有する。編集された行だけが書き込み時に複製される（COW）。
- 素のままの行は保存時にそのまま書き戻す（`Text::raw_line`）。エスケープの
  知識は `format` だけが持ち、`format::document::read` が「`$` を含まない行は
  素のまま」という不変条件を守る。
- 実測（release、素のテキスト 100 MB・200 万行）: 読み込み 0.5 秒、
  保存 0.6 秒、可視 100 行の展開 1.2 ms、文字数集計 0.2 秒。
- 残る限界:
  - IPC は依然として全文を 1 つの文字列で渡すので、数百 MB でメモリと転送が
    重い（第 3 段で解消）。
  - 全選択コピー・検索・すべて置換は全行を `Row` に展開する。
  - 履歴 1 ステップにつき行ポインタの配列（1 行 8 バイト）を持つ。

### 第 3 段: 文書の本体を native に置く（1 GB 級）— 実装済み

frontend（wasm）にファイル全体を渡すのをやめ、本体をネイティブ側の
`store::Document` にした。編集・元に戻す・保存・検索の走査・大きなコピーは
本体が行い、frontend は「行範囲の置き換え」を送り、`read_lines` で窓を
取り寄せるだけ。取り寄せ・編集・元に戻す・保存・下書き・コピー・検索は
タブごとに 1 本の列で本体へ届くので、行番号は食い違わない。

- 文書は行数だけの `Text::pending` として先に画面へ出る。見えた場所の行から
  取り寄せ、まだ届かない行は空の行として見える。届いていない行に触れる編集
  だけが何もしない（読み込み中ロックは無い）。
- 元に戻す履歴は本体の逆操作ログ。同じグループの置き換えは 1 ステップに
  つながり、「すべて置換」も 1 回で戻る。キャレットの控えは本体に預ける。

### 第 4 段: 本文をメモリに置かない・ビューは窓（実装済み）

- **native は本文を持たない。** 開くときは先頭 1 MB を読み、残りの改行数えと
  間引き索引の構築はバックグラウンドで続ける。控えるのは 1024 行（`STRIDE`）
  ごとの行頭のバイト位置だけ。行の中身は最寄りの索引へ seek して読み流す。
  文書はピース列（ディスクに残る行の範囲｜編集で入った行）で、メモリは索引と
  編集量の分だけ。Ctrl+End は確定行数を待たず、EOFから末尾の窓を先に表示し、
  行番号は確定後に絶対位置へ付け替える。
- 実測（release、800 MB・1600 万行）: 開く 0.7 秒、中程の 100 行の読み 2 ms、
  native の常駐メモリ約 70 MB（以前は約 1.3 GB）。
- 保存は一時ファイルへ流してから入れ替え、書きながら次の索引を作って
  保存先を新しい本体にする。外部でファイルが書き換えられたら、壊れた
  seek 読みを返さずに「開き直してください」と断る（mtime とサイズで検知）。
- **ビューはファイルを覗く窓。** 文書をブラウザーにスクロールさせず、
  ページに置くのは窓の先頭行から画面を満たす数十行だけ。縦の動きは
  窓の先頭行がすべてを決め、ホイールは行数で、つまみ（数千 px の専用
  要素）は文書全体の割合で動かす。Ctrl+End や検索の一致へは目的行の窓を
  直接描く。巨大な場所取り要素も圧縮座標も無い。
- wasm 側は手元の行が 2 万行を超えると、可視窓の前後 5 千行、選択行、
  未送信の編集行を残して遠い行を未着へ戻す。戻った場所は native から再取得する。
- 検索欄への入力中は可視窓だけを同期検索して移動せずにハイライトする。全文件数は
  等間隔の行窓から約 12.8 万行を標本として推定する。次の一致までは検索開始時の
  ピースを独立したファイルハンドルで native の1ジョブとして走査し、文書ロックを
  持たない。新しい検索や編集は古いジョブを中止する。通常文字列は大小区別ありと
  ASCIIの大小無視を、ディスク範囲をまとめて読むバイト検索で処理する。

### 巨大ファイル対応の状況（Phase 3 完了時点）
- **下書き（自動控え）とクラッシュ復旧**: 実装済み。全文を書き出さず「元ファイル参照 + 操作ログ（差分） + 削除行」の形式で記録するため、下書きサイズは元ファイルの巨大さに比例せず「未保存の差分ペイロード（編集・Undo量）」のみにスケールし、通常編集であれば数ミリ秒・最小限のサイズで下書き保存され、未保存の Undo/Redo や Clean 状態からの Redo 復元を含めて完全に対象となる。
- **大きなファイルの「すべて置換」**: 文書エンジン内部で遅延一括操作（BulkRule）としてログに記録し、表示・保存時にストリーム適用するネイティブ基盤を実装済み（UI / IPC への完全配線は Phase 4 以降で実施）。

### リファクタリング完了後の検討課題（外部更新・ファイルロック・Tail監視）
大リファクタリング（Phase 4 以降）完了後に詰めるべき重要な運用・保護機能：

1. **外部更新の検知と下書きの整合性管理**:
   - 別プロセスによって元ファイルが更新された場合の検知（mtime/ファイルサイズ判定、または OS ファイル監視）。
   - 外部で元ファイルが書き換わると、下書きに記録された「元ファイルのバイト位置・行番号」の整合性が壊れるため、安全に下書きファイル群を破棄（または開き直しを促す警告表示）。
   - 可能であれば、未保存の差分を退避・活かして外部変更と安全に突き合わせる更新フローの検討。
2. **リアルタイム Tail モード（ログ閲覧・読み込み専用）**:
   - 巨大ログファイル等を開くための「読み込み専用（Read-only）」モード。
   - 外部からの末尾追記をリアルタイムに監視し、インデックスを追従伸長させながら画面を自動リフレッシュする `tail -f` 的な追尾機能。
3. **巨大ファイル編集時の排他制御（ファイルロック）**:
   - 巨大ファイルを編集モードで開く際、他プロセスによる不用意な同時編集や上書き破損を防ぐための安全なファイルロック機構の導入。

## この順で出す理由

- 第 1 段だけで、実際に開けるファイルの大きさが 2 桁変わる（描画が今の上限）。
  しかも `view` の中で終わるので、意味の層のテストはそのまま通る。
- 第 2 段は `Text` の外向きの形を変えないので、第 1 段の上に独立して積める。
  ここで初めて `structure` のテストが「持ち方に依らない」ことの検査になる。
- 第 3 段は IPC とファイル入出力の形が変わる（唯一 UI に影響が出る段: 開いた
  瞬間に全文の文字数を数えられなくなるので、ステータスバーの「N 文字」は
  「読んだところまで」か「行数だけ」に変わる）。

## 変えないもの

- 保存形式。
- 層の境界（`structure` は `view` / `editor` / `format` を知らない、など）。
- 「普通のテキストとして読み書きする」書き味。折り返し・行番号・列揃え・島の
  編集はすべて今のまま。
